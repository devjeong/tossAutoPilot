## 0. 한 줄 정의

**TossAutoPilot**은 토스증권 Open API를 쓰는 **서버 상주 자동매매 웹 서비스**다.  
사용자는 브라우저로 포트폴리오·전략·리스크를 관리하고, **매매 판단·주문 전송은 브라우저가 아닌 서버 엔진**이 수행한다.

## 1. 기존 제품 분석 (AUTO_TRADE_VER2)

### 1.1 제품 성격

| 항목 | 상태 |
|---|---|
| 플랫폼 | Electron + React + TypeScript (Windows 데스크톱) |
| 엔진 위치 | 로컬 메인 프로세스 (앱이 꺼지면 전략도 멈춤) |
| 자격증명 | Windows DPAPI 로컬 암호화 |
| 인증 모델 | 단일 사용자 · 로컬 전용 (계정 시스템 없음) |
| 주문 | 수동 전송 연결됨 + 전략 자동전송 **opt-in** 연결됨 |
| 모의투자 | 토스 샌드박스 **없음** → 데모 데이터 + 클라이언트 dry-run 개념 |
| 테스트 | vitest 다수 (게이트·전략·백테스트·주문 경로 등) |

### 1.2 아키텍처 강점 (웹에서도 **반드시 계승**)

기존 코어의 설계 원칙은 웹에서도 제품 정체성이다. 재작성 시 “예쁘게” 바꾸기보다 **이 계약들을 유지**한다.

| # | 원칙 | 근거 (코드/스펙) |
|---|---|---|
| P1 | **판단 불가는 통과가 아니다** | 게이트·전략 모두 null/미수신 → BLOCK 또는 신호 없음 |
| P2 | **모든 주문은 게이트 10개 통과** | `src/core/risk/gates.ts` — 첫 BLOCK에서 멈추지 않고 전부 평가 |
| P3 | **전송 직전 재평가** | 화면 판정을 믿지 않음. 수동·자동 동일 |
| P4 | **자동전송은 opt-in** | `RUNNING`(감시+큐) ≠ `autoSendEnabled`(무인 전송) |
| P5 | **멱등키(`clientOrderId`)** | 네트워크 재시도 시 중복 주문 방어의 유일한 선 |
| P6 | **금액·수량은 decimal 고정소수점** | float 경계 흔들림 → 주문 오발주 방지 |
| P7 | **Rate Limit 15그룹 독립 버킷** | 토큰 버킷 + 헤더 보정 + 동시성 우선순위 |
| P8 | **시세 transport 격리** | 폴링 구현을 인터페이스 뒤에 둠 (추후 스트림 교체) |
| P9 | **민감정보 마스킹** | 토큰·시크릿 로그 금지 |
| P10 | **매도는 유의종목이어도 막지 않음** | 손절 불능을 막기 위함 (매수만 차단) |

### 1.4 데스크톱 제품의 구조적 한계 (웹이 해결해야 할 것)

| # | 한계 | 영향 | 웹에서의 방향 |
|---|---|---|---|
| L1 | **앱 종료 = 엔진 종료** | 무인 매매가 “PC 켜둔 동안만” | 서버(또는 상주 워커) 24/7 엔진 |
| L2 | 자격증명이 로컬 | 기기 이전·재설치·다중 기기 취약 | 서버 측 암호화 보관, 브라우저에 시크릿 금지 |
| L3 | 단일 프로세스 UI 결합 | UI 프리즈·업데이트 시 위험 | UI ↔ 엔진 분리, 엔진 독립 배포 |
| L4 | 상태 영속성 약함 | 재시작 시 트레이스·저널 유실 가능 | DB 영속 (주문·신호·저널·캔들) |
| L5 | 샌드박스 없음 + dry-run UX 약함 | 실수 시 실주문 위험 | Dry-run / Paper 모드를 기본 온보딩으로 |
| L6 | 조건주문 쓰기 미연결 | 익절·손절 자동화 공백 | API 쓰기 경로 완성 |
| L7 | 정정(modify) 미연결 | 추적 지정가·미체결 관리 약함 | 정정 API + UI |
| L8 | 시각 전략 편집기 부재 | 그래프 전략 생산성 낮음 | MVP는 폼 기반 basic-v1, 편집기는 이후 |
| L9 | 멀티 테넌시 없음 | 서비스화 불가 | (개인용 단일 계정이라도) 유저·세션 모델 필요 |
| L10 | 모바일/원격 킬 스위치 불가 | 외출 중 위험 대응 어려움 | 웹/텔레그램 킬 스위치 |

### 1.5 계승할 코어 모듈 후보 (로직 이전)

웹 재구축 시 **UI는 새로 쓰되**, 아래 도메인 로직은 포팅 가치가 높다.

```
core/risk/*          게이트 · 가격규칙 · 리스크 엔진
core/rateLimit/*     토큰 버킷 · 그룹
core/strategy/*      basicV1 · graph · runner · evaluator · indicators
core/backtest/*      백테스터 (evaluate 공유 원칙)
core/api/*           엔드포인트 · zod 스키마
core/http/*          클라이언트
core/auth/tokenManager
core/util/decimal · redact · backoff
core/alert/*         텔레그램 · 시장 분위기 (서버 배치)
```

Electron 전용(`main/*`, `preload/*`, DPAPI, IPC)은 **폐기**하고 서버 API + 실시간 채널로 대체한다.

## 2. 개선해야 할 것 (Improve)

웹으로 옮기면서 **같은 기능을 더 안전하게 / 더 명확하게** 만드는 항목.

### I1. 엔진을 서버로 이전 (최우선 구조 개선)

- 브라우저 탭은 **관제실**, 서버는 **조종석**.
- 전략 tick, 폴링, 주문 전송, 토큰 갱신은 전부 서버.
- 브라우저 종료·절전·네트워크 끊김이 매매를 멈추지 않게 한다.
- 단, **서버↔토스 API 단절** 시 기존 N7 정책 계승: 전략 HOLD, 자동 재개 금지, 사용자 확인.

### I2. 자격증명·시크릿 모델

| 데스크톱 | 웹 (개선) |
|---|---|
| Client ID/Secret 로컬 DPAPI | 서버 vault (암호화 at-rest). 브라우저·프론트 번들에 절대 포함 금지 |
| 토큰 메모리 | 서버 메모리/암호화 저장 + 선제 갱신 |
| 로그 마스킹 | 동일 + 접근 감사 (누가 설정 변경했는지) |

> 토스 Open API가 Client Credentials 기반인 한, “사용자 비밀번호로 토스 로그인”이 아니라 **API 키를 서비스에 위탁**하는 모델이다. 온보딩에 **위험 고지·철회 절차**를 명시한다.

### I3. Dry-run / Paper를 1급 기능으로

기존: `dryRun` 플래그는 있으나 UX·강제 경로가 약하고, 실주문 테스트 가이드에 의존.

개선:

1. **Paper(Dry-run)**: 게이트·신호·주문 본문까지 생성하되 `POST /orders` 호출 금지. 저널에 `WOULD_SUBMIT` 기록.
2. **Live**: 명시적 전환. 전환 시 이중 확인 + 리스크 한도 요약 표시.
3. 신규 연결 직후 기본값 = **Paper**.
4. 전략별 자동전송은 Live에서만 가능. Paper에서는 자동전송 스위치 비활성 또는 시뮬레이션만.

### I4. 주문·조건주문 쓰기 경로 완성

| 경로 | 개선 목표 |
|---|---|
| 주문 생성 | 유지 (수동·자동 공통 게이트) |
| 주문 취소 | 유지 |
| 주문 정정 | **신규 연결** (KR 수량 필수 / US 수량 금지 분기) |
| 조건주문 CRUD | **등록·수정·취소 연결** + 진입 체결 후 OCO 자동 등록 |
| 미체결/조건 재동기화 | 재기동·재연결 시 API 기준 재동기화 (N6) |

### I5. 감사 가능 저널 (재현성)

기존: 구조화 로그 방향은 맞으나 로컬 휘발성.

웹 요구:

- 이벤트 영속: `SIGNAL → GATE → SUBMIT|BLOCK → ACK → FILL/CANCEL`
- 게이트별 verdict 스냅샷, 요청 본문(마스킹 후), 응답 코드
- UI에서 주문 1건 클릭 시 **타임라인 재생**
- 보관 기간·내보내기(CSV/JSON)

### I6. 킬 스위치 · 원격 안전장치

- 웹 헤더 상시 노출 + 확인 모달
- 텔레그램 명령 (예: `/kill`, `/status`) — 기존 명령 폴링 확장
- 킬 시: 전 전략 정지 + autoSend off + (설정 시) 미체결 전량 취소
- 해제는 웹에서만, 쿨다운 또는 재확인

### I7. Rate Limit을 멀티 세션/멀티 화면에 맞게

- 폴링 예산은 **계좌(또는 API 키) 단위 1버킷** — 탭을 여러 개 열어도 서버가 한 번만 폴링
- UI는 SSE/WebSocket으로 스냅샷 수신 (클라이언트가 토스 API를 직접 두드리지 않음)

### I8. UX 정보 구조 (3-모드 계승 + 웹 네비)

기존 3-모드(홈 / 트레이딩 / 전략)는 철학적으로 우수 → **유지**.

웹 개선:

- 좌측 또는 상단 네비 + URL 라우팅 (`/`, `/trade`, `/strategies`, `/orders`, `/journal`, `/settings`)
- 홈 = Daylight Ledger (평온·명료)
- 트레이딩 = Quiet Instrument (고밀도, 데스크톱 우선)
- 전략 = Signal Board (목록·파라미터·트레이스·백테스트; 배선 편집기는 이후)
- 모바일: 홈·킬스위치·대기 큐·알림 위주. 고밀도 호가 트레이딩은 **데스크톱 권장** 배너.

### I9. 온보딩 · 안전 기본값

1. 서비스 위험 고지 (실계좌·실주문, 샌드박스 없음)
2. API 키 등록 (서버 저장)
3. 연결 확인 (계좌·시세)
4. **Paper 모드에서 전략 1개 돌려보기**
5. 테스트 안전 한도 프리셋 (기존 “10만원 상한” 등) 적용 후 Live 전환

### I10. 설정·상태 불일치 정리

- 데스크톱 UI 카피/푸터에 “자동전송 없음” vs 코드상 opt-in 존재 같은 **문서·UI 불일치**를 웹에서는 단일 상태 모델로 통일.
- 전략 카드에 항상 표시: `상태` · `자동전송` · `Paper/Live` · `마지막 평가` · `대기 큐 수`.

## 5. 제품 원칙 (TossAutoPilot)

1. **안전이 기능이다.** 게이트·킬스위치·Paper 모드는 부가 기능이 아니라 제품.
2. **무인은 명시적 opt-in.** 기본은 감시, 전송은 따로 켠다.
3. **서버가 진실의 원천.** UI 상태는 투영일 뿐, 재연결 시 서버·거래소 기준으로 재동기화.
4. **재현 가능성.** “왜 샀는가”를 저널로 답할 수 있어야 한다.
5. **낙관 금지.** 백테스트·체결 가정·수수료 기본값은 보수적.
6. **토스 API 제약을 숨기지 않는다.** 폴링 지연, 캔들 1m/1d, 샌드박스 없음을 UI에 정직하게 표기.

## 9. 상태 모델 (요약)

### 9.1 엔진

`stopped` → `starting` → `running` ⇄ `degraded` → `error` → (사용자) `stopped`

### 9.2 전략

```
PAUSED ──start──▶ RUNNING ──stale/data──▶ HOLD
                      │                    │
                      │ autoSend opt-in    │ resume(user)
                      ▼                    ▼
                 (live only)            RUNNING
                 submit path
```

### 9.3 주문 의도

`SIGNAL` → `GATE_PASS|GATE_BLOCK` → (`paper`: `WOULD_SUBMIT`) | (`live`: `SUBMITTED` → `OPEN` → `PARTIAL` → `FILLED`) / `CANCELLED` / `REJECTED`

## 10. MVP 범위 선언

### 10.1 MVP에 넣는다

- 로그인(단일 운영자)
- 토스 키 서버 보관 · 연결 · 데모 모드
- Paper / Live
- 홈 · 트레이딩 · 전략(basic-v1) · 주문 · 저널 · 설정
- 게이트 10 + 킬 스위치
- 수동 주문 · 취소 · 전략 자동전송 opt-in (live)
- 조건주문 자동 등록(진입 후 OCO) + 목록 조회
- 백테스트 (동기 또는 단순 job)
- 텔레그램 알림
- 영속 저널·전략·설정

### 10.2 MVP에 넣지 않는다

- 노드 시각 편집기
- TWAP/VWAP
- 풀 시장 스크리너
- 팀/RBAC
- 웹 푸시 · 이메일 리포트
- 주문 정정·조건주문 수동 고급 편집 (정정은 P1로 바로 이어도 됨)
- 모바일 완전 대응 트레이딩 뷰

### 10.3 성공 기준 (MVP Done)

1. Paper에서 전략 신호를 하루 돌려도 **실주문이 0건**
2. Live 소액 수동 주문 왕복 (지정가 → 미체결 확인 → 취소) 성공
3. 자동전송 opt-in 전략 1건이 게이트 통과 후 실접수되고 저널에 전 구간 남음
4. 킬 스위치 1회에 전송 중단이 확인됨
5. 서버 재시작 후 상태 복구·재동기화
